## 1. 技术栈

- Next.js App Router（`output: "standalone"`，Turbopack）+ TypeScript；Prisma + PostgreSQL 16（Docker）；`node --test` 单测（非 vitest）
- 部署：puer-hk 服务器 amd64 本地 docker build；nginx 前置（静态/反代）；MinIO 容器在跑但**代码未使用**（见 §6）
- 测试 `npm run test:unit`；迁移手工 psql apply（先 SQL 后镜像，铁律见 docs/release-checklist.md）
- 入口 `/` 308 → `/forum`；`/tw/*` 繁体镜像树

- **评分双轨**：`TastingNote` 有五维**独立列** appearance/color/aroma/taste/aftertaste（Int，schema 注释 1–5，API 实际校验 0–10，两处口径不一致）；`Article.tastingScores` 是 Json 列但发布管线**设计上从不写入**（茶记管线明确约束「分数永不写入」）。茶品页聚合读的是 TastingNote 五维列（`src/lib/tea-stats.ts` → `Tea.avgRating`）。
- `site_daily_stats` 游离表（无 model，$queryRaw 读）；`article_views` 去重浏览表已有（articleId+visitorKey+day 唯一）。
- 迁移 10 个，全部手工 apply；最近一个即今天的 reviewFeedback。

## 3. 评分口径 —— 需站长决策（PRD 待确认 1 的落地）

- 现状没有「综合评分」标量列；用户感知的评分是 Tea.avgRating（五维均值的聚合）与帖子里的五维条。
- PRD 四维（香气/滋味/水路/体感，1–10）与现有五维（外观/汤色/香气/滋味/回甘）**维度与量纲都不同**。
- 待决策：a) 四维作为**新增列**与五维并存（老笔记走 F1 回填到四维，五维列保留不动）；b) 四维替换五维（回填后废弃五维展示）。PRD 倾向「只增不删」，默认按 a。

## 4. 内容发布管线现状（F0 映射）

| 管线 | 机制 | F0 对应 |
|---|---|---|
| 茶记（AI 基于站长笔记） | `tasting-draft_<noteId>` 确定性 id = 天然 source_note_ids；aiOriginal 存 AI 原版；draft→人工审核→发布 | origin=ai_from_notes 的数据几乎现成，补标注列即可 |
| 全自动资讯（PentAGI 检索→改写） | `news-draft_<hash>`；teaId=null 不碰品鉴数据；单一署名账号 puer-news；draft→人工审核→发布 | 站长已决策：独立固定用户、不进茶记/品鉴，对 PRD 无影响；上线标注（origin=ai_autonomous +「AI 生成 · 非站长品鉴」）归入 F0 统一做 |
| 人工发帖 | 常规 API | origin=human 默认 |

审核页（/admin/drafts）已有：来源笔记并排展示（resolveSourceNote）、待重写徽章、退回/发布/删除。F0 要求的「事实逐项勾选核对」「定时发布每日上限/暂停开关」未实现。

## 6. 图片存储链路（PRD §8 反滥用落点）

- 唯一上传口 `POST /api/upload`（分片+单次），登录强制；**写本地磁盘** `public/uploads/<subdir>/<uuid>.<ext>`，返回相对 URL。MinIO 容器/minio-setup 在 compose 里且 app 收到 MINIO_* env，但**代码零引用**；NEXT_PUBLIC_MINIO_URL 指向 nginx 未代理的路径（死配置）。
- nginx（deploy/nginx/puer.conf）对各 uploads 子目录 alias 直出，expires 30d，**无防盗链、无签名 URL**。
- **已有**：sharp 水印（上传时纹理铺满、原地覆写，头像除外）；HEIC/AVIF→JPEG 转换；重编码默认丢 EXIF；视频 ffmpeg 720p+缩略图。
- **缺**：原图私有化（现在覆写后即唯一版本，无原图留存可私有化——需要改成「存原图+发水印版」）；分辨率降档（现无尺寸限制压缩）；防盗链；会员签名 URL 机制（连 MinIO client 都要新引）。
- **发现的 bug**：compose 卷挂载漏了 `avatars`/`.tmp`/`videos-raw` 三个子目录 → 容器重建后头像丢失、分片上传状态丢失。

## 7. 通知能力（F4 落点）

- `Notification` 表已有（type: reply|upvote|mention|system|essence），但**只有评论回复触发**（notifyCommentReply）；点赞/投票/@提及不通知（type 只是字面量）；**无标记已读 API**（铃铛只读）。
- 无任何邮件能力（无 nodemailer/resend，无 SMTP env）。
- F4 的「站内通知」有底子（加提醒触发点+已读），「邮件月度汇总」需从零搭。

## 8. 指标与防护（F0 指标重算、§8 反滥用落点）

- 无 DAU/留存模型；管理页有注册/发帖趋势 + site_daily_stats 浏览趋势（$queryRaw）。
- viewCount 双轨：旧 SSR 渲染 +1（无去重）仍在用；新去重链路（view-beacon→article_views）已建但未回写。
- 限速：内存版 rate-limit.ts（登录/注册/发帖/QA 各有阈值，按 IP）；**无 middleware 级限速/封禁**（src/proxy.ts 只做 locale）；无翻页深度限制；无批量遍历检测。
- **robots.txt 不存在**——PRD 的 AI 爬虫声明需要从零建。
- 条款页存在（/terms /privacy，文本硬编码），需按 PRD 补授权/禁止抓取条款。

## 9. SEO / 路由现状

sitemap.ts 动态生成（forum/tea/classics/tasting 等全部收录）；无 robots.txt（与上节同一条）；`/tea` 在 sitemap 且页面公开（仅导航入口对非管理员隐藏，昨天已上线）；URL/帖子 id 未变过——PRD 的「不得改变 URL」现状满足。

## 10. 与 PRD 不一致 / 需要站长确认的决策点（汇总）

1. **四维 vs 五维**（§3）：默认四维新增列、五维保留为 overall_legacy 展示，待你确认。
2. **editor 角色**：现状 role 只有 user|admin，你本人应为 admin。PRD 的 editor 是新 role 值，还是站长线直接锚定「原始笔记的 authorId=你」？默认后者（不加 role，避免权限面扩大）。
3. **自动化账号**：259 个合成账号标 isSynthetic=true（§5 的域名清单请过目——尤其确认 `@puer.tea`/`@mock.local` 里没有你要保留为真人的账号）。
4. **历史冒用数据**：真实用户被 auto-vote/auto-reply 冒用产生的历史投票/评论，按 PRD「保留记录、剔除展示计数」——**剔除展示**涉及热榜/计数重算，是否 Phase 0 就做，还是先只锁池子（新动作不再冒用）？默认先锁池子，剔除随后。

7. **auto-register 停不停**：它每天造 3–5 个新合成账号。锁定后它注册的账号应自动 isSynthetic=true；若 Phase 0 要做「真实用户增长」，这个脚本是否暂停？默认：保留注册但标记，等你决定。

### 12.1 顺带查出并修掉的三个真实缺陷

1. **无水印原片在容器重建后全部消失** —— `videos-raw` 既没挂载也没进 Dockerfile，宿主有 130 个原片但容器读不到，管理员「无水印下载」长期静默回落到带水印版。
2. **无水印原片其实可被公网按文件名直接下载** —— 它们位于 `public/uploads/videos-raw/` 下，`/uploads/videos-raw/<name>.mp4` 可直接取到，水印形同虚设。现已移出 `public/`，并加 nginx 兜底拒绝。
3. **头像并没有丢** —— 9 个头像全部写在 `/uploads/forum/`（前端从不传 `category=avatar`），而 `forum` 是有挂载的。`avatars/` 目录至今为空壳。已补挂载消除隐患。

### 12.2 生产库口径修正（schema 与实际不符）

- `TastingNote` schema 注释写「各维度 1-5」，实际值域 5–9，API 校验 0–10 —— **注释过时**，以 API 为准。
- 1752 款茶中只有 **2 款**有 `avgRating`；1109 款有笔记。评分体系基本没启用，四维迁移不急。

## 16. 反滥用上线记录（2026-10-22）

镜像 `puer-hub-app:20261022T223716Z-antiaabuse`。

**三层防护**

| 层 | 位置 | 口径 | 阈值 |
|---|---|---|---|
| IP 级 | `src/proxy.ts`（Next 16 的 proxy 约定） | X-Forwarded-For 首值 | 120 次/分钟；连续撞线 3 次 → 封禁 30 分钟 |
| 账号级 | 路由层（articles / teas） | 已加载的会话 | 60 次/分钟 |
| 翻页深度 | 路由层 | 匿名/普通用户 | 单页 ≤60、页 ≤50、feed offset ≤300 |

管理员一律不受限 —— 后台要 `/api/teas?limit=9999` 一次拉全量茶品。

**防盗链**：8 个 uploads location 加 `valid_referers none puer.im *.puer.im`。
`none` 必须留（去掉它会让无 Referer 的取图——服务端脚本、小红书发布管线、
邮件、微信图片代理——全部 403）。实测：无 Referer 200 / 本站 200 /
子域 200 / 第三方 403。

**feature flag**：新增 `src/lib/feature-flags.ts`，生产 .env 显式开启，
compose 透传进容器（改 .env + `docker compose up -d app` 即生效，不必重建镜像）。
环境变量值写错时按代码默认值处理而不是静默关闭 —— 保护性功能被一个拼错的
变量悄悄关掉，比不生效更危险。

**两点必须说清的局限**

1. **Cloudflare 缓存会让防盗链只对缓存未命中的请求生效**。已在 CF 缓存里的
   图片，CF 直接返回给任何 Referer。真正的防抓取保护是 PRD §8 的
   「公开展示版加水印 + 原图私有 + 限速」，防盗链只是补一层。
2. **限速与封禁状态在内存里，容器重启即清空**。符合「临时封禁」的语义，
   但也意味着重启是绕过封禁的最快方式。

**踩过的两个坑（都已修）**

- nginx 备份文件放在 `sites-enabled/` 里 → 通配 include 把它也加载了，
  产生 conflicting server name 警告并影响生效块。备份必须放 `/etc/nginx/`
  下（仓库文档里记过这个坑）。
- 测限速时从本机连打 130 次没触发：每次 curl 经 CF 约 0.8 秒，130 个请求
  摊在 2 分钟以上，60 秒窗口从未攒够 120 个。**限速测试必须从服务器本地打**，
  否则测的是网络延迟不是限速。
